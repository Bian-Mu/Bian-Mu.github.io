
### 事件循环

#### 浏览器的进程

进程：程序运行时专属的内存空间，至少一个，可以通信但需要双方同意
线程：程序中划分多类任务由对应的线程运行，使用进程的内存空间，随进程启动的是主线程  

浏览器为了避免崩溃，将开启多个互不影响的进程，主要如下：

1. 浏览器进程：负责窗口及本体功能、交互、子进程的管理，其他进程由它启动
2. 网络进程：网络资源的加载
3. 渲染进程（默认每个标签页各一个，沙盒）：启动后，开启一个渲染主线程，负责三件套的执行

渲染进程过多，chrome目前正在调整以避免高内存占用...，可能会改为每个站点一个渲染进程

#### 渲染主线程

主要任务：

1. html、css的解析
2. css的计算
3. 布局
4. 图层排布
5. 每秒画60次维持帧率
6. 执行js函数
7. 执行事件处理函数
8. 执行计时器的回调函数

主线程不将任务分成多个线程的原因是？

##### 任务调度与消息队列

当6、7、8两两相遇时，必须要进行调度

消息队列：将线程中的任务排入队列。

渲染主线程在生成后会进入无限循环：（事件循环）

1. 检查消息队列中有无任务，有则将第一个任务取出并执行，执行结束后才进入下一次循环；无则进入休眠
2. 渲染进程的其他线程、其他进程的线程都可以随时在队列中添加任务，默认队尾，此时如果渲染主线程在休眠，则唤醒

#### 循环中的QA

##### JS的异步

JS运行在唯一的渲染主线程中，所以代码在执行时部分任务不能立刻处理，例如前置计时`setTimeout`、前置网络通信`fetch`、前置用户交互`addEventListener`

不能因为等待这些任务而进入阻塞：这些任务将会在被主线程交给对应线程后立刻离开主线程，对应线程执行完后将回调函数包装为新任务重新插入队列等待主线程调度

##### JS影响渲染

```html
<body>
    <h1>awesome!</h1>
    <button>change</button>
    <script>
      var h1 = document.querySelector('h1');
      var btn = document.querySelector('button');

      function delay(duration) {
        var start = Date.now();
        while (Date.now() - start < duration) {}
      }

      btn.onclick = function () {
        h1.textContent = '帅！';
        delay(3000);
      };
    </script>
  </body>
```

上述代码实际表现为先delay再修改textContent：

1. 交互线程监听到click后将fn插入消息队列
2. 主线程更改h1内容，并将新页面渲染任务插入消息队列
3. 主线程执行delay，delay结束后主线程接收并执行新页面渲染

react-vibe可以控制js执行时长

##### 任务的优先级

任务无优先级，但消息队列有优先级。每个任务都有对应的任务类型，同类任务必须在同一队列，不同类型可以在不同队列。

在一次循环中，浏览器会根据实际情况从不同队列中取出。浏览器自身的微队列中的任务优先于所有任务

目前chrome中有至少有以下队列：

1. 延时队列：计时器对应的回调任务，中
2. 交互队列：交互行为的事件处理任务，高
3. 微队列：最高

- 将任务插入微队列`Promise.resolve().then(fn)`

##### JS不能精确计时

内置计时器本质是调用了操作系统的函数，其本身就有偏差。同时浏览器计时器一旦嵌套超过5层，最少需要额外4ms；而受限于事件循环，计时后的回调只能等待在队列中，又有误差。

### 浏览器的渲染原理

所谓渲染，就是将html:string计算成screen上的pixels

#### 渲染的时间点

1. 网络线程获取html后包装成渲染任务插入消息队列
2. 渲染主线程在事件循环中取出任务并“渲染”，每步都是从输入->输出
   1. 解析html：将html parse成dom树与cssom树。启动预解析线程来先浏览、下载`<link>`中的css/js、css汇总后交给主线程变成cssom树，因此主线程不会等待`<link>`，所以css不会导致阻塞；但js涉及改动，因此主线程将立刻暂停等待预解析线程汇总后执行。执行后最终得到dom树
   2. 样式计算：主线程遍历dom树，借助cssom树依次计算出每个节点的最终样式computed style，预设值会变成绝对值，形成有样式的dom树
   3. 布局：样式dom树中包含位置、尺寸、父子等布局样式，auto等特殊值在此也在此完成，计算后形成layout树（不保证与dom树对应，如`display:none`、`::before`等）
   4. 分层：由于页面不是静止的，所以需要确定层级来减少重绘（可以通过will-change样式来单独成层，减少对其他部分的影响）
   5. 绘制：此处指的是为每一层生成具体要如何paint的指令集。渲染主线程交接后暂时结束工作。
   6. 分块：合成线程将从线程池中调用数个分块器线程，共同将每一层tiling成多个小区域tiles，来便于优先绘制视口区域等
   7. 光栅化：GPU进程得到tiles，raster成位图（完成像素设置），优先处理视口区域的tiles，此过程使用显卡。
   8. 画画：合成线程得到每层、每块的位图后，生成`quad`（指引）标识出每个位图应该在屏幕的哪个位置、同时考虑形变（因与主线程无关，故`transform`等效率高），GPU进程根据`quad`产生系统调用，由硬件完成draw

- dom树：document object model，以对象形式存储节点，便于js处理
- cssom树：css object model，以对象形式存储stylesheets，包括内部`<style>`、外部`<link>`、行内`<div style="">`、浏览器默认的样式表，根据规则与选择器生长
- 合成线程：来自渲染进程
- GPU进程：来自浏览器

#### reflow

当cssom或者dom发生改变并导致几何信息改变时，2-8步都需要再次执行，其中最耗时的是layout，reflow指的就是layout的重新计算

浏览器的优化：为了避免连续多次操作导致反复计算，浏览器会对“改写”操作合并，可以当所有js都完成后再统一计算，从而实现异步。但是异步会导致无法立刻获取最新的属性值，因此当出现“读取”的操作时，reflow立刻发生

#### repaint

当只改动类似“颜色”的属性时，layout与layer可能可以跳过，此时来到repaint

### 属性描述符

一个属性具有很多可以被描述的内容，例如：

1. value 值
2. writable 写
3. enumerable 是否可被遍历到
4. configurable 描述符本身是否可以修改
5. get/set 函数，为读写行为配置默认行为,与1和2互斥存在

- 描述一个对象的某一个属性，可以通过`Object.getOwnPropertyDescriptor(objA, propA)`，一般是一个对象
- 可以重新定义描述符`Object.defineProperty(objA, propA, newDescA)`
- 冻结一个对象`Object.freeze(objA)`来避免直接增改原始数据，可以冻结原型
- 密封一个对象`Object.seal(objA)`允许改但不允许加

### 微前端

微前端是一种将单体前端应用拆分为多个独立、可自治的子应用的架构模式，每个子应用可独立开发、部署和运行。核心优势包括：

- 技术栈解耦：不同子应用可使用 React、Vue、Umi 等不同框架
- 团队自治：各团队独立迭代，互不干扰
- 按需加载：主应用通过微前端框架（如 micro-app、qiankun）动态加载子应用
- 渐进式升级：逐步替换旧模块，降低重构风险
