
### TCP vs UDP

| 特性              | TCP (传输控制协议)                                                     | UDP (用户数据报协议)                                   |
| :---------------- | :--------------------------------------------------------------------- | :----------------------------------------------------- |
| **连接性**        | 面向连接，通信前需建立连接（三次握手）。                               | 无连接，直接发送数据。                                 |
| **可靠性**        | 可靠，通过序列号、确认应答、重传机制保证数据不丢失、不重复、按序到达。 | 不可靠，尽力而为地交付，不保证数据到达、顺序或完整性。 |
| **速度**          | 较慢，因为需要建立连接和保证可靠性，开销较大。                         | 较快，开销小，传输效率高。                             |
| **流量/拥塞控制** | 有，通过滑动窗口和拥塞控制算法来控制发送速率。                         | 无。                                                   |
| **通信方式**      | 点对点。                                                               | 支持一对一、一对多、多对多。                           |
| **头部开销**      | 头部较大，至少20字节。                                                 | 头部较小，仅8字节。                                    |

- **TCP**：适用于要求高可靠性的场景，如文件传输（FTP）、电子邮件（SMTP）、网页浏览（HTTP）。
- **UDP**：适用于对实时性要求高、能容忍少量丢包的场景，如视频流、在线游戏、DNS查询。

### 三次握手 & 四次挥手

#### 三次握手 (连接建立)

TCP通过三次握手来建立一个可靠的连接。

1. 第一次握手：客户端发送一个 SYN（同步序列编号）报文给服务器，并进入 SYN_SENT 状态，等待服务器确认。
2. 第二次握手：服务器收到 SYN 报文后，必须确认客户的 SYN（ack=x+1），同时自己也发送一个 SYN 包（seq=y），即 SYN+ACK 包，此时服务器进入 SYN_RECV 状态。
3. 第三次握手：客户端收到服务器的 SYN+ACK 包后，向服务器发送确认包 ACK（ack=y+1），此包发送完毕，客户端和服务器进入 ESTABLISHED 状态，完成三次握手。

- 主要是为了防止已失效的连接请求报文段突然又传送到了服务端，从而产生错误。如果只有两次握手，服务器收到一个过期的连接请求就会立即建立连接，并等待客户端发送数据，这会浪费服务器资源。三次握手确保了双方都确认了对方的发送和接收能力。

#### 四次挥手 (连接断开)

TCP连接是全双工的，因此每个方向都必须单独进行关闭。

1. 第一次挥手：客户端发送一个 FIN（结束）报文，用来关闭客户端到服务器的数据传送，客户端进入 FIN_WAIT_1 状态。
2. 第二次挥手：服务器收到 FIN 报文后，发送一个 ACK 给客户端，确认序号为收到序号+1。此时，TCP连接处于半关闭状态，即客户端已经没有数据要发送了，但是服务器若发送数据，客户端依然要接受。
3. 第三次挥手：服务器发送 FIN 报文，用来关闭服务器到客户端的数据传送，服务器进入 LAST_ACK 状态。
4. 第四次挥手：客户端收到 FIN 报文后，发送 ACK 报文作为应答，并进入 TIME_WAIT 状态。服务器收到 ACK 后，立即进入 CLOSE 状态。客户端等待2个MSL（最长报文段寿命）后，也进入 CLOSE 状态。

- 因为TCP是全双工的，当一方（如客户端）发送 FIN 请求关闭时，只表示它不再发送数据了，但仍然可以接收数据。另一方（服务器）可能还有数据没发送完，所以不能立即关闭。服务器会先回复一个 ACK 表示收到了关闭请求，等自己所有数据都发送完毕后，再发送 FIN 来关闭自己的发送通道。

### 可靠传输机制

1. 流量控制 (Flow Control)：
   - 目的是防止发送方发送数据太快，导致接收方缓冲区溢出。
   - 通过滑动窗口 (Sliding Window) 机制实现。接收方在 ACK 报文中会包含自己的接收窗口大小，发送方根据这个窗口大小来调整自己的发送速率。

2. 拥塞控制 (Congestion Control)：
   - 目的是防止过多的数据注入到网络中，导致网络过载。
   - 主要有四种算法：
     1. 慢启动 (Slow Start)：连接刚建立时，指数级增加拥塞窗口（cwnd）大小。
     2. 拥塞避免 (Congestion Avoidance)：当拥塞窗口超过一个阈值后，改为线性增加，以避免增长过快导致网络拥塞。
     3. 快重传 (Fast Retransmit)：当发送方连续收到三个相同的 ACK 时，就认为有数据包丢失，立即重传该数据包，而不必等待超时。
     4. 快恢复 (Fast Recovery)：当触发快重传时，将阈值减半，拥塞窗口设置为新的阈值，然后执行拥塞避免算法，而不是像超时重传那样直接降为1。

### 粘包/拆包

#### 原因

1. TCP是基于字节流的协议，没有消息边界。
2. 粘包：发送方连续发送的多个小数据包，在TCP缓冲区中可能会被合并成一个大的数据包一次性发送出去。
3. 拆包：要发送的数据大于TCP缓冲区大小或MSS（最大报文段长度）时，数据会被拆分成多个数据包发送。

#### 解决方法

粘包和拆包是应用层需要解决的问题。

1. 消息定长：发送方和接收方约定一个固定的消息长度，不足则用特殊字符填充。
2. 特殊分隔符：在每个消息的末尾加上一个特殊的分隔符（如\r\n）。
3. 头部加长度字段：在消息的头部添加一个字段，用于描述整个消息的长度。
