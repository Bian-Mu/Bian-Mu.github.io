### 1. 体系结构

#### **OSI七层模型 vs TCP/IP四层模型**

计算机网络体系结构主要有两种模型：OSI七层模型和TCP/IP四层模型。OSI模型是一个理论上完整的模型，而TCP/IP模型是目前事实上的工业标准。

*   **OSI七层模型**：由国际标准化组织（ISO）提出，旨在为网络通信提供一个标准框架。 它将网络功能划分为七个独立的层次：
    1.  **物理层 (Physical Layer)**：负责传输原始的比特流，定义了电压、接口、线缆规范等。
    2.  **数据链路层 (Data Link Layer)**：负责在直接相连的节点间进行可靠的数据传输，进行物理寻址（MAC地址）、错误侦测和改错。
    3.  **网络层 (Network Layer)**：负责在网络中为数据包选择最佳路径（路由），进行逻辑寻址（IP地址）。
    4.  **传输层 (Transport Layer)**：提供端到端的通信服务，负责数据分段、流量控制和错误恢复。
    5.  **会话层 (Session Layer)**：负责建立、管理和终止两个通信主机之间的会话连接。
    6.  **表示层 (Presentation Layer)**：负责数据的格式化、加密和压缩，确保一个系统的应用层所发送的信息可以被另一个系统的应用层读取。
    7.  **应用层 (Application Layer)**：为用户应用程序提供网络服务接口。

*   **TCP/IP四层模型**：是互联网的基础，更为精简和实用。
    1.  **网络接口层 (Network Interface Layer)**：对应OSI的物理层和数据链路层。
    2.  **网络层 (Internet Layer)**：对应OSI的网络层。
    3.  **传输层 (Transport Layer)**：对应OSI的传输层。
    4.  **应用层 (Application Layer)**：对应OSI的会话层、表示层和应用层。

**主要区别**：
*   **分层数量**：OSI是七层，TCP/IP是四层（或有时被称为五层，即将网络接口层分为物理层和数据链路层）。
*   **实践性**：OSI是理论模型，先有模型后有协议；TCP/IP是实践中产生的，先有协议和应用后有模型，是事实上的标准。

#### **各层常见的协议**

*   **物理层**：规定了物理设备标准，如网线、网卡、集线器的接口类型和传输介质。
*   **数据链路层**：以太网 (Ethernet)、PPP (Point-to-Point Protocol)。
*   **网络层**：
    *   **IP (Internet Protocol)**：互联网协议，负责数据包的路由和寻址。
    *   **ICMP (Internet Control Message Protocol)**：互联网控制报文协议，用于发送错误和控制消息（如 `ping` 命令）。
*   **传输层**：
    *   **TCP (Transmission Control Protocol)**：传输控制协议，提供面向连接、可靠的字节流服务。
    *   **UDP (User Datagram Protocol)**：用户数据报协议，提供无连接、不可靠的数据报服务。
*   **应用层**：
    *   **HTTP (HyperText Transfer Protocol)**：超文本传输协议，用于Web浏览器和服务器之间的通信。
    *   **DNS (Domain Name System)**：域名系统，用于将域名解析为IP地址。
    *   **FTP (File Transfer Protocol)**：文件传输协议。
    *   **SMTP (Simple Mail Transfer Protocol)**：简单邮件传输协议。

### 2. TCP/UDP (传输层)

#### **TCP vs UDP**

| 特性              | TCP (传输控制协议)                                                     | UDP (用户数据报协议)                                   |
| :---------------- | :--------------------------------------------------------------------- | :----------------------------------------------------- |
| **连接性**        | 面向连接，通信前需建立连接（三次握手）。                               | 无连接，直接发送数据。                                 |
| **可靠性**        | 可靠，通过序列号、确认应答、重传机制保证数据不丢失、不重复、按序到达。 | 不可靠，尽力而为地交付，不保证数据到达、顺序或完整性。 |
| **速度**          | 较慢，因为需要建立连接和保证可靠性，开销较大。                         | 较快，开销小，传输效率高。                             |
| **流量/拥塞控制** | 有，通过滑动窗口和拥塞控制算法来控制发送速率。                         | 无。                                                   |
| **通信方式**      | 点对点。                                                               | 支持一对一、一对多、多对多。                           |
| **头部开销**      | 头部较大，至少20字节。                                                 | 头部较小，仅8字节。                                    |

**应用场景**：
*   **TCP**：适用于要求高可靠性的场景，如文件传输（FTP）、电子邮件（SMTP）、网页浏览（HTTP）。
*   **UDP**：适用于对实时性要求高、能容忍少量丢包的场景，如视频流、在线游戏、DNS查询。

#### **三次握手 & 四次挥手**

**三次握手 (连接建立)**
TCP通过三次握手来建立一个可靠的连接。

1.  **第一次握手**：客户端发送一个 `SYN`（同步序列编号）报文给服务器，并进入 `SYN_SENT` 状态，等待服务器确认。
2.  **第二次握手**：服务器收到 `SYN` 报文后，必须确认客户的 `SYN`（`ack=x+1`），同时自己也发送一个 `SYN` 包（`seq=y`），即 `SYN+ACK` 包，此时服务器进入 `SYN_RECV` 状态。
3.  **第三次握手**：客户端收到服务器的 `SYN+ACK` 包后，向服务器发送确认包 `ACK`（`ack=y+1`），此包发送完毕，客户端和服务器进入 `ESTABLISHED` 状态，完成三次握手。

*   **为什么要3次？**
    *   主要是为了防止已失效的连接请求报文段突然又传送到了服务端，从而产生错误。如果只有两次握手，服务器收到一个过期的连接请求就会立即建立连接，并等待客户端发送数据，这会浪费服务器资源。三次握手确保了双方都确认了对方的发送和接收能力。

**四次挥手 (连接断开)**
TCP连接是全双工的，因此每个方向都必须单独进行关闭。

1.  **第一次挥手**：客户端发送一个 `FIN`（结束）报文，用来关闭客户端到服务器的数据传送，客户端进入 `FIN_WAIT_1` 状态。
2.  **第二次挥手**：服务器收到 `FIN` 报文后，发送一个 `ACK` 给客户端，确认序号为收到序号+1。此时，TCP连接处于半关闭状态，即客户端已经没有数据要发送了，但是服务器若发送数据，客户端依然要接受。
3.  **第三次挥手**：服务器发送 `FIN` 报文，用来关闭服务器到客户端的数据传送，服务器进入 `LAST_ACK` 状态。
4.  **第四次挥手**：客户端收到 `FIN` 报文后，发送 `ACK` 报文作为应答，并进入 `TIME_WAIT` 状态。服务器收到 `ACK` 后，立即进入 `CLOSE` 状态。客户端等待2个MSL（最长报文段寿命）后，也进入 `CLOSE` 状态。

*   **为什么要4次？**
    *   因为TCP是全双工的，当一方（如客户端）发送 `FIN` 请求关闭时，只表示它不再发送数据了，但仍然可以接收数据。另一方（服务器）可能还有数据没发送完，所以不能立即关闭。服务器会先回复一个 `ACK` 表示收到了关闭请求，等自己所有数据都发送完毕后，再发送 `FIN` 来关闭自己的发送通道。

*   **TIME_WAIT 状态**
    *   **作用**：
        1.  **保证可靠的关闭**：确保最后发送的 `ACK` 报文能够到达对方。如果这个 `ACK` 丢失，对方会超时重传 `FIN`，有 `TIME_WAIT` 状态的客户端可以重新发送 `ACK`。
        2.  **防止已失效的报文段出现**：防止本次连接中滞留在网络中的报文段，在连接关闭后又出现在下一个相同四元组（源IP、源端口、目的IP、目的端口）的连接中。等待2MSL可以确保本次连接的所有报文段都从网络中消失。
    *   **过多的危害**：如果服务器上有大量处于 `TIME_WAIT` 状态的连接，会占用大量的端口资源和内存资源，可能导致新的连接无法建立。

#### **可靠传输机制**

TCP通过多种机制来保证数据传输的可靠性。

*   **流量控制 (Flow Control)**：
    *   目的是防止发送方发送数据太快，导致接收方缓冲区溢出。
    *   通过**滑动窗口 (Sliding Window)** 机制实现。接收方在 `ACK` 报文中会包含自己的接收窗口大小，发送方根据这个窗口大小来调整自己的发送速率。

*   **拥塞控制 (Congestion Control)**：
    *   目的是防止过多的数据注入到网络中，导致网络过载。
    *   主要有四种算法：
        1.  **慢启动 (Slow Start)**：连接刚建立时，指数级增加拥塞窗口（cwnd）大小。
        2.  **拥塞避免 (Congestion Avoidance)**：当拥塞窗口超过一个阈值后，改为线性增加，以避免增长过快导致网络拥塞。
        3.  **快重传 (Fast Retransmit)**：当发送方连续收到三个相同的 `ACK` 时，就认为有数据包丢失，立即重传该数据包，而不必等待超时。
        4.  **快恢复 (Fast Recovery)**：当触发快重传时，将阈值减半，拥塞窗口设置为新的阈值，然后执行拥塞避免算法，而不是像超时重传那样直接降为1。

#### **粘包/拆包**

*   **原因**：
    *   TCP是基于字节流的协议，没有消息边界。
    *   **粘包**：发送方连续发送的多个小数据包，在TCP缓冲区中可能会被合并成一个大的数据包一次性发送出去。
    *   **拆包**：要发送的数据大于TCP缓冲区大小或MSS（最大报文段长度）时，数据会被拆分成多个数据包发送。

*   **解决方法**：粘包和拆包是应用层需要解决的问题。
    1.  **消息定长**：发送方和接收方约定一个固定的消息长度，不足则用特殊字符填充。
    2.  **特殊分隔符**：在每个消息的末尾加上一个特殊的分隔符（如`\r\n`）。
    3.  **头部加长度字段**：在消息的头部添加一个字段，用于描述整个消息的长度。

### 3. HTTP/HTTPS (应用层)

#### **HTTP 状态码**

HTTP状态码是服务器对客户端请求的响应。

*   **200 OK**: 请求成功。
*   **301 Moved Permanently**: 永久重定向。请求的资源已被永久移动到新的URL。
*   **302 Found**: 临时重定向。请求的资源临时从不同的URL响应。
*   **304 Not Modified**: 缓存。资源未被修改，客户端可以使用缓存的版本。
*   **401 Unauthorized**: 未授权。需要用户身份验证。
*   **403 Forbidden**: 禁止访问。服务器理解请求，但拒绝执行。
*   **404 Not Found**: 未找到。服务器上没有找到请求的资源。
*   **500 Internal Server Error**: 服务器内部错误。服务器遇到了一个未曾预料的状况，导致了它无法完成对请求的处理。
*   **502 Bad Gateway**: 网关错误。作为网关或代理的服务器，从上游服务器收到了无效的响应。
*   **504 Gateway Timeout**: 网关超时。作为网关或代理的服务器，未能及时从上游服务器接收响应。

#### **HTTP 版本演变**

*   **HTTP/1.0 vs 1.1**：
    *   **长连接 (Keep-Alive)**：1.1默认开启长连接，允许在一个TCP连接上发送多个HTTP请求，减少了连接建立和关闭的开销。
    *   **Host头字段**：1.1增加了Host头，使得一台服务器可以托管多个域名。
    *   **更多的状态码和缓存控制**。

*   **HTTP/1.1 vs 2.0**：
    *   **多路复用 (Multiplexing)**：在一个TCP连接上可以并行发送多个请求和响应，解决了1.1中的队头阻塞问题。
    *   **头部压缩 (Header Compression)**：使用HPACK算法压缩请求和响应的头部，减少了传输开销。
    *   **服务端推送 (Server Push)**：服务器可以主动向客户端推送资源，而无需客户端明确请求。

*   **HTTP/3.0**：
    *   **基于QUIC协议**：QUIC（Quick UDP Internet Connections）是基于UDP的协议。
    *   **解决了TCP的队头阻塞问题**：如果QUIC中一个流的数据包丢失，不会影响其他流的传输。
    *   **更快的连接建立**：结合了TCP和TLS的握手过程，减少了连接建立的延迟。

#### **GET vs POST**

GET和POST是HTTP协议中最常用的两种请求方法。

| 特性         | GET                                                     | POST                                                                 |
| :----------- | :------------------------------------------------------ | :------------------------------------------------------------------- |
| **语义**     | 从服务器获取资源。                                      | 向服务器提交数据，导致资源状态的改变或产生副作用。                   |
| **参数位置** | 参数附加在URL后面，对用户可见。                         | 参数放在请求体（Request Body）中，对用户不可见。                     |
| **安全性**   | 不安全，因为参数暴露在URL中，且会留在浏览器历史记录里。 | 相对安全，参数在请求体中，不会被缓存或保留在历史记录里。             |
| **幂等性**   | 幂等，多次相同的GET请求，结果应该相同。                 | 非幂等，多次相同的POST请求，可能会产生不同的结果（如多次创建资源）。 |
| **长度限制** | URL长度受浏览器限制。                                   | 无长度限制。                                                         |
| **缓存**     | 结果可以被浏览器缓存。                                  | 结果默认不会被缓存。                                                 |

#### **HTTPS**

HTTPS (HTTP Secure) 是通过SSL/TLS协议对HTTP通信进行加密的版本。

*   **TLS/SSL 握手流程**：
    HTTPS的核心在于建立一个安全的信道，这个过程通过TLS/SSL握手完成，它混合使用了对称加密和非对称加密。
    1.  **客户端Hello**：客户端向服务器发送支持的TLS版本、密码套件和一个随机数（Client Random）。
    2.  **服务器Hello**：服务器选择一个双方都支持的密码套件，并返回其数字证书、一个随机数（Server Random）。
    3.  **客户端验证与密钥交换**：
        *   客户端验证服务器证书的有效性。
        *   验证通过后，客户端再生成一个随机数（Pre-Master Secret），并用证书中的公钥加密后发送给服务器。
    4.  **服务器解密与会话密钥生成**：
        *   服务器用自己的私钥解密得到 Pre-Master Secret。
        *   现在，客户端和服务器都拥有了三个随机数（Client Random, Server Random, Pre-Master Secret），双方使用相同的算法各自生成一个对称的会话密钥。
    5.  **握手完成**：双方互发“加密握手结束”消息，确认后续将使用这个会话密钥进行对称加密通信。

*   **数字证书的原理**：
    *   **目的**：解决公钥在传输过程中被篡改的问题，即确认公钥持有者的身份。
    *   **CA (Certificate Authority)**：可信任的第三方证书颁发机构。
    *   **原理**：
        1.  网站运营者向CA申请证书，提供自己的域名和公钥。
        2.  CA用自己的私钥对网站的公钥和相关信息进行签名，生成数字证书。
        3.  客户端（如浏览器）内置了所有受信任CA的公钥。当收到服务器的证书时，用对应的CA公钥来验证签名的有效性，从而确认服务器公钥的真实性。

#### **Cookie vs Session**

Cookie和Session都是用来在无状态的HTTP协议中维持会话状态的机制。

| 特性           | Cookie                                   | Session                                                |
| :------------- | :--------------------------------------- | :----------------------------------------------------- |
| **存储位置**   | 客户端（浏览器）。                       | 服务器端。                                             |
| **安全性**     | 较低，数据暴露在客户端，易被篡改和窃取。 | 较高，只在客户端存储一个Session ID，敏感数据在服务器。 |
| **数据大小**   | 受限，通常不超过4KB。                    | 理论上无限制，但受服务器内存影响。                     |
| **生命周期**   | 可设置较长的过期时间。                   | 通常在用户关闭浏览器后失效，或在服务器端超时后失效。   |
| **服务器压力** | 无。                                     | 占用服务器内存资源。                                   |

**分布式Session解决方案**：
在分布式或负载均衡环境中，用户的请求可能被分发到不同的服务器，导致基于单机内存的Session失效。
1.  **Session粘滞 (Sticky Sessions)**：通过负载均衡器（如Nginx的ip_hash）将同一用户的请求始终定向到同一台服务器。
2.  **Session复制**：在集群中的多台服务器之间同步Session数据。缺点是同步会带来网络开销。
3.  **Session共享 (外部存储)**：将Session数据集中存储在外部服务中，如 **Redis** 或 Memcached。这是目前最主流的方案。
4.  **JWT (JSON Web Token)**：一种无状态的认证方案。服务器通过私钥对用户信息生成一个Token并发送给客户端。客户端在后续请求中携带此Token，服务器用公钥验证Token的合法性即可，无需在服务器端存储任何Session信息。

### 4. 经典综合题

#### **从在浏览器输入 URL 到页面展示，发生了什么？**

这是一个全链路问题，串联了上述几乎所有知识点。

1.  **URL解析**：浏览器首先解析用户输入的URL，判断是搜索内容还是一个合法的URL。如果是URL，则提取出协议（HTTP/HTTPS）、域名、端口、路径等信息。

2.  **缓存检查**：浏览器检查自身缓存中是否有请求的资源。首先是强缓存（Expires, Cache-Control），如果命中则直接使用缓存，不发送HTTP请求。如果没有命中强缓存，则会检查协商缓存（Last-Modified, ETag），并带上相应的头字段发送请求。

3.  **DNS解析**：如果缓存中没有，浏览器需要将URL中的域名解析为对应的IP地址。
    *   检查浏览器自身DNS缓存。
    *   检查操作系统Hosts文件和本地DNS缓存。
    *   向本地DNS服务器发起递归查询。
    *   本地DNS服务器会从根域名服务器开始，进行迭代查询，最终找到域名对应的IP地址。

4.  **建立TCP连接**：浏览器使用获取到的IP地址和端口号（HTTP默认80，HTTPS默认443），与服务器发起TCP连接，进行**三次握手**。

5.  **TLS握手**：如果URL是HTTPS协议，在TCP连接建立后，还需要进行**TLS握手**，协商加密密钥，建立安全连接。

6.  **发送HTTP请求**：TCP连接建立后，浏览器构建并发送一个HTTP请求报文（包含请求行、请求头、请求体）。

7.  **服务器处理请求**：服务器（如Nginx、Tomcat）接收到请求后，会进行处理。这可能包括：
    *   解析请求，定位到具体的应用程序。
    *   处理业务逻辑，可能涉及数据库查询等操作。
    *   构建一个HTTP响应报文（包含状态码、响应头、响应体）。

8.  **接收HTTP响应**：浏览器接收到服务器的响应报文。

9.  **关闭TCP连接**：根据HTTP头部的`Connection`字段（`keep-alive`或`close`），浏览器决定是保持连接还是通过**四次挥手**关闭TCP连接。

10. **浏览器渲染页面**：
    *   **解析HTML**：浏览器将HTML文本解析成DOM（文档对象模型）树。
    *   **解析CSS**：将CSS解析成CSSOM（CSS对象模型）树。
    *   **构建渲染树 (Render Tree)**：将DOM和CSSOM结合，生成渲染树。渲染树只包含需要显示的节点及其样式信息。
    *   **布局 (Layout/Reflow)**：根据渲染树计算每个节点在屏幕上的确切位置和大小。
    *   **绘制 (Paint)**：调用GPU，将各个节点绘制到屏幕上。
    *   在解析HTML过程中，如果遇到`<script>`标签，可能会阻塞DOM的构建，去加载和执行JavaScript。JavaScript代码可能会修改DOM和CSSOM，导致重新布局和绘制（Reflow & Repaint）。
