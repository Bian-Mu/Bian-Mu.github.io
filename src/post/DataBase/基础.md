
### 存储引擎（以MySQL为例）

| 特性         | InnoDB                                                                                          | MyISAM                                                                            |
| ------------ | ----------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| **事务支持** | **支持**，完全符合 ACID 特性，支持提交（Commit）和回滚（Rollback）。                            | **不支持**，操作是原子性的，但不支持事务回滚。                                    |
| **锁级别**   | **行级锁（Row-level Locking）**，并发性能更高，只锁定需要修改的行，减少了多用户操作时的冲突。   | **表级锁（Table-level Locking）**，一个写操作会锁定整张表，导致并发写入性能较差。 |
| **外键约束** | **支持**，可以强制实施参照完整性。                                                              | **不支持**。                                                                      |
| **崩溃恢复** | **支持**，通过事务日志（Redo Log 和 Undo Log）可以实现安全的崩溃恢复。                          | **不支持**，更容易发生数据损坏。                                                  |
| **适用场景** | 适用于需要高并发、事务处理和数据完整性的应用，如在线交易系统（OLTP）。是 MySQL 的默认存储引擎。 | 适用于读密集型、对事务要求不高的应用，如数据仓库或静态网站。                      |

### 索引原理：B+树

#### 为什么用B+树而不用其他数据结构？

- 二叉树/红黑树：这些树结构虽然在内存中效率很高，但它们是为二元查找设计的。在数据量巨大、需要存储在磁盘上的数据库中，它们的树高会非常深。由于每次节点访问都可能对应一次磁盘 I/O，过深的树会导致大量的磁盘读写，性能急剧下降。
- Hash 表：哈希索引对于等值查询（如 WHERE id = 100）的性能极佳，时间复杂度为 O(1)。但它的缺点是无法支持范围查询（如 WHERE id > 50），因为哈希后的值是无序的。
- B+树的优势：
  - 磁盘 I/O 优化：B+树的节点可以存储多个关键字，这使得它的“扇出”（fan-out）非常高，从而让整个树的高度变得很低。 树的高度降低意味着从根节点到叶子节点需要访问的节点数减少，即磁盘 I/O 次数减少，这对于磁盘密集型的数据库至关重要。
  - 范围查询友好：B+树的所有数据都存储在叶子节点，并且这些叶子节点通过指针相互连接，形成一个有序的双向链表。 这种结构使得范围查询和排序操作变得非常高效，只需在叶子节点层进行顺序遍历即可。

#### 聚簇索引 vs 非聚簇索引

- 聚簇索引 (Clustered Index)：在 InnoDB 中，表数据本身就是按照主键的顺序存放在 B+树的叶子节点上。因此，一张表只能有一个聚簇索引（通常是主键）。 查找聚簇索引可以直接定位到完整的数据行。
- 非聚簇索引 (Non-clustered/Secondary Index)：非聚簇索引的叶子节点存储的是索引键的值以及对应行的主键值。
- 回表查询 (Key Lookup)：当使用非聚簇索引进行查询时，如果查询的列不完全包含在索引中，数据库引擎会先通过该索引找到对应的主键，然后再使用主键去聚簇索引中查找完整的行数据。这个过程被称为“回表”。

#### 覆盖索引、最左前缀匹配原则

- 覆盖索引 (Covering Index)：如果一个索引包含了查询所需的所有列（SELECT、WHERE、ORDER BY 等子句中涉及的列），那么数据库就无需再回表查询，可以直接从索引中获取所有数据并返回。 这种情况下的索引就称为覆盖索引，能显著提升查询性能。
- 最左前缀匹配原则：对于一个多列复合索引 (col1, col2, col3)，查询条件必须从索引的最左边的列开始，并且不能跳过中间的列，索引才能被充分利用。例如，WHERE col1 = 'a' 或 WHERE col1 = 'a' AND col2 = 'b' 都能使用该索引，但 WHERE col2 = 'b' 则无法使用。

#### 索引优化

索引失效的常见情况：

- 使用 LIKE 并以通配符 % 开头，如 LIKE '%keyword'。
- 对索引字段进行函数运算、计算或表达式操作，如 WHERE YEAR(create_time) = 2023。
- 发生隐式类型转换，如索引字段是字符串类型，但在查询时使用了数字 WHERE phone_number = 123456。

Explain 命令的使用：EXPLAIN 是一个强大的查询优化工具，可以放在 SELECT 语句前，用于分析查询的执行计划。 它可以显示 MySQL 如何连接表、使用何种类型的索引、扫描了多少行等信息，帮助开发者诊断慢查询并进行针对性优化。

### 事务与锁

事务是数据库管理系统执行过程中的一个逻辑单位，由一个或多个SQL语句组成，这些语句要么全部执行，要么全部不执行。

#### ACID 特性

ACID 是指数据库事务正确执行的四个基本要素：

- 原子性 (Atomicity)：事务被视为一个不可分割的最小工作单元，整个事务中的所有操作要么全部提交成功，要么全部失败回滚。
- 一致性 (Consistency)：事务必须使数据库从一个一致性状态转变到另一个一致性状态。
- 隔离性 (Isolation)：一个事务的执行不能被其他事务干扰。即一个事务内部的操作及使用的数据对并发的其他事务是隔离的。
- 持久性 (Durability)：一个事务一旦被提交，它对数据库中数据的改变就是永久性的。

#### 隔离级别

为了平衡数据一致性和并发性能，SQL 标准定义了四种隔离级别。 MySQL 的 InnoDB 引擎全部支持，默认级别是可重复读 (Repeatable Read)。

| 隔离级别                        | 脏读 (Dirty Read) | 不可重复读 (Non-Repeatable Read) | 幻读 (Phantom Read)                   |
| ------------------------------- | ----------------- | -------------------------------- | ------------------------------------- |
| **读未提交 (Read Uncommitted)** | 可能              | 可能                             | 可能                                  |
| **读已提交 (Read Committed)**   | 不可能            | 可能                             | 可能                                  |
| **可重复读 (Repeatable Read)**  | 不可能            | 不可能                           | 可能 (InnoDB 通过 Next-Key Lock 解决) |
| **串行化 (Serializable)**       | 不可能            | 不可能                           | 不可能                                |

- 脏读：一个事务读取到了另一个事务未提交的数据。
- 不可重复读：一个事务内多次读取同一数据，但得到的结果不同。这是因为在读取间隔，另一个事务修改了该数据并已提交。
- 幻读：一个事务内多次执行同样的范围查询，但第二次查询的结果集包含了一些第一次查询中没有的“幻影”行。这是因为在读取间隔，另一个事务插入了新的数据。

#### MVCC (多版本并发控制)

MVCC 是一种并发控制方法，它通过保存数据在某个时间点的快照来实现。 在 InnoDB 中，MVCC 使得读操作不用阻塞写操作，写操作也不用阻塞读操作，极大地提升了并发性能。 MVCC 主要在 READ COMMITTED 和 REPEATABLE READ 这两个隔离级别下工作。

原理 (Undo Log + Read View)：

- Undo Log：当数据被修改时，InnoDB 会将旧版本的数据写入 Undo Log。 这样，一行数据就可能存在多个历史版本，形成一个版本链。
- Read View：当一个事务开始时（在 RR 级别）或每条查询开始时（在 RC 级别），InnoDB 会创建一个 Read View。 这个 Read View 本质上是当前数据库中所有活跃（未提交）事务 ID 的一个列表快照。
- 可见性判断：当事务要去读取某一行数据时，它会根据该行记录的事务 ID 和自己的 Read View 进行比较，沿着 Undo Log 的版本链回溯，直到找到一个对当前事务可见的版本。

解决了什么问题：MVCC 的主要目标是在不加锁或少加锁的情况下解决读写冲突，实现了“非阻塞读”，从而提高了数据库的并发处理能力。它有效地解决了脏读和不可重复读的问题。

### Redis (缓存)

Redis 作为一个高性能的内存数据库，常被用作 MySQL 的前端缓存，以减轻数据库压力，提升应用响应速度。提供了丰富的数据类型来满足不同的业务需求：

- String (字符串)：最基本的数据类型，可以存储文本、数字甚至二进制数据。场景：缓存用户信息、Session 共享、分布式锁、计数器（如文章点赞数）。
- List (列表)：一个字符串链表，按照插入顺序排序，可以在头部或尾部进行快速的插入和删除操作。场景：消息队列、任务队列、微博或朋友圈的时间线。
- Set (集合)：无序的、不重复的字符串集合。支持高效的成员检查和集合间运算（交、并、差集）。场景：共同好友、抽奖系统、标签系统（为用户或文章打标签）。
- ZSet (有序集合/Sorted Set)：与 Set 类似，但每个成员都会关联一个 double 类型的分数（score），并根据分数进行排序。场景：排行榜、带权重的任务队列、范围查找（如价格区间筛选）。
- Hash (哈希)：一个键值对的集合，非常适合存储对象。场景：存储用户信息（如用户名、年龄、邮箱等字段）、购物车。

#### RDB vs AOF

Redis 提供了两种主要的持久化机制，以确保内存中的数据不会因为服务器重启而丢失。

| 特性     | RDB (Redis Database)                                                                                                                           | AOF (Append Only File)                                                                                               |
| -------- | ---------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| **原理** | 在指定的时间间隔内，将内存中的数据集快照写入磁盘，生成一个 `dump.rdb` 文件。                                                                   | 以日志的形式记录服务器所处理的每一个写操作命令。服务器重启时，会重新执行 AOF 文件中的命令来恢复数据。                |
| **优点** | 1. 文件紧凑，非常适合备份和灾难恢复。 2. 恢复速度比 AOF 快，因为直接加载二进制文件。 3. 对性能影响小，父进程只需 fork 一个子进程来进行持久化。 | 1. 数据安全性更高，可以配置为每秒同步（everysec），最多只会丢失1秒的数据。 2. 文件是可读的追加格式，易于理解和修复。 |
| **缺点** | 1. 数据一致性较差，如果 Redis 意外宕机，会丢失最后一次快照之后的所有修改。 2. fork 子进程在数据集较大时可能会消耗一定的时间和CPU资源。         | 1. AOF 文件通常比 RDB 文件大。 2. 恢复速度相对较慢。 3. 在高写入负载下，AOF 的性能可能略低于 RDB。                   |

#### 过期策略与内存淘汰策略

- 过期策略：Redis 如何删除过期的键。
    1. 定期删除：Redis 默认每秒进行10次过期扫描，随机抽取一些设置了过期时间的键进行检查，并删除其中的过期键。
    2. 惰性删除：当客户端访问一个键时，Redis 会先检查该键是否过期，如果过期则删除，并返回空。这是为了弥补定期删除可能漏掉过期键的情况。
- 内存淘汰策略：当 Redis 内存使用达到 maxmemory 上限时，需要通过某种策略来删除一些键以腾出空间。常见的策略包括：
    1. LRU (Least Recently Used)：淘汰最近最少使用的键。
    2. LFU (Least Frequently Used)：淘汰使用频率最低的键。
    3. Random：随机淘汰。
    4. TTL：淘汰最接近过期的键。

#### 缓存三大坑

1. 缓存穿透 (Cache Penetration)
    - 问题：查询一个不存在的数据。由于缓存中没有，请求会直接打到数据库，而数据库中也没有，所以不会写入缓存。如果大量请求都查询这个不存在的数据，就会给数据库带来巨大压力。
    - 解决方案：布隆过滤器 (Bloom Filter)。 这是一个空间效率极高的概率型数据结构，它可以判断一个元素“一定不存在”或者“可能存在”。 在查询前先通过布隆过滤器判断 key 是否可能存在，如果判断为不存在，就直接返回，避免了对后端存储的查询。
2. 缓存击穿 (Cache Breakdown)
    - 问题：一个热点 Key（访问量极高）在某个时刻突然过期失效。此时，大量并发请求会同时涌向数据库来重建缓存，可能瞬间压垮数据库。
    - 解决方案：互斥锁 (Mutex Lock)。 当缓存失效时，只允许一个线程去查询数据库并重建缓存，其他线程则等待。获取到锁的线程完成缓存重建后，其他线程就可以直接从缓存中获取数据。
3. 缓存雪崩 (Cache Avalanche)
    - 问题：大量的 Key 在同一时间集中过期，或者 Redis 服务器宕机。这导致大量的请求瞬间直接访问数据库，造成数据库压力剧增甚至崩溃。
    - 解决方案：随机化过期时间。在原有的过期时间基础上，增加一个随机值（例如1-5分钟），这样可以打散 key 的过期时间，避免集中失效。

#### Redis 分布式锁

在分布式系统中，多个服务实例需要协调对共享资源的访问，此时需要分布式锁。

1. SETNX + LUA 脚本：SETNX (SET if Not eXists) 命令可以尝试设置一个键，只有在该键不存在时才会成功，这可以用来获取锁。 但简单的 SETNX 和 EXPIRE 组合不是原子操作，可能在 SETNX 成功后、EXPIRE 执行前服务崩溃，导致死锁。为了保证原子性，通常使用 Lua 脚本将“加锁并设置过期时间”这两个操作封装在一起，由 Redis 服务端原子性地执行。
2. Redlock：这是 Redis 官方提出的一个分布式锁算法，它通过在多个独立的 Redis 实例上获取锁来提高锁的可靠性。 客户端需要成功地从大多数（例如，5个实例中的3个）实例中获取到锁，才算真正地获取了分布式锁。这解决了单点故障问题，但实现更复杂。
