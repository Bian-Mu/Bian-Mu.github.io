
### 分层架构 (Layered Architecture) - 后端核心

这是最经典且在企业级应用（如 Java Spring Boot, Go Gin 等）中最为普遍的架构，它将系统在纵向上切分为多个职责明确的层次。

在实际项目中，通常会细分为以下几层：

1. 接入层 / API 层 (Controller / Interface)
    - 职责：作为系统的入口，负责接收外部请求（HTTP, RPC）。
    - 工作内容：
        1. 参数解析与基础校验（Validation）。
        2. DTO (Data Transfer Object) 转换：将请求体转换为内部业务对象。
        3. 统一响应封装（Result/Response结构）。
    - 关键组件：中间件 (Middleware) 通常作用于此层之前或之中，用于处理跨切面关注点，如：
        1. 身份认证 (Authentication) & 权限校验 (Authorization)。
        2. 日志记录 (Logging)：记录请求入参、出参、耗时。
        3. 全局异常处理 (Global Exception Handling)。
        4. 限流与熔断。
2. 业务逻辑层 (Service Layer)
    - 职责：系统的核心，承载具体的业务流程和规则。
    - 工作内容：
        1. 编排业务流程（例如：下单 = 校验库存 -> 扣减库存 -> 创建订单 -> 发送通知）。
        2. 事务管理 (Transaction)：确保操作的原子性，要么全成功，要么全回滚。
        3. 调用第三方服务（如支付接口、短信服务）。
    - 设计思路：Service 层应保持无状态，且不应直接处理 HTTP 相关的对象（如 Request/Response），以保证逻辑的可复用性和可测试性。
3. 数据访问层 (DAO / Repository)
    - 职责：与数据库或其他持久化存储进行交互。
    - 工作内容：
        1. CRUD 操作。
        2. ORM 映射（将数据库行映射为对象）。
        3. 屏蔽底层存储细节（MySQL, Redis, MongoDB）。
4. 基础设施层 (Infrastructure)
   - 提供通用的技术支持，如工具类、配置管理、消息队列客户端等。

### MVC (Model-View-Controller)

MVC 主要用于解决界面展示与业务逻辑的耦合问题，但在前后端分离的今天，其形态发生了变化。
传统 MVC：服务端渲染 (SSR)，Controller 直接返回 HTML 页面。现代 Web 开发中的 MVC：
后端：退化为只提供 JSON 数据接口（Controller 对应 API 层，Model 对应 Service/Entity）。
前端：接管了 View 的渲染逻辑。

### MVVM (Model-View-ViewModel) - 前端核心

现代前端框架（React, Vue, Angular）的主流架构。

- Model: 数据模型（来自后端 API 的数据）。
- View: UI 组件（HTML/CSS）。
- ViewModel:
    1. 双向绑定：View 的变化自动更新 Model，Model 的变化自动刷新 View。
    2. 状态管理：在复杂应用中，ViewModel 的概念往往扩展为全局状态管理（如 Redux, Vuex, Pinia），用于解决组件间通信和状态共享问题。

### 领域驱动设计 (DDD, Domain-Driven Design)

用户接口层 (UI)：处理外部请求（Web, API）。
应用层 (Application)：编排业务流程，不包含核心业务逻辑。
领域层 (Domain)：包含核心业务逻辑、概念和规则（实体、值对象、聚合）。
基础设施层 (Infrastructure)：提供通用技术支持（数据库、消息队列、缓存）

### 微服务架构 (Microservices)

将单体应用拆分为多个独立部署的服务。

1. 关键组件与设计API 网关 (API Gateway)：
    - 作为所有微服务的统一入口（Nginx, Kong, Spring Cloud Gateway）。
    - 负责路由转发、协议转换、统一鉴权、流量控制。
2. BFF (Backend for Frontend)：
    - 为不同客户端（App, Web, 小程序）聚合数据，裁剪接口。
3. 服务间通信：
    - 同步：RESTful API (HTTP) 或 RPC (gRPC, Dubbo)。
    - 异步：消息队列 (Kafka, RabbitMQ) 实现解耦。
4. 注册中心：服务发现。
5. 配置中心：动态管理配置。
6. 链路追踪：分析跨服务的调用链性能。

### 事件驱动架构 (Event-Driven Architecture)

核心：组件之间不直接调用，而是通过事件 (Event) 进行通信。
场景：

1. 解耦：用户注册成功后，发送“注册成功事件”。邮件服务监听发邮件，积分服务监听送积分。邮件服务挂了不影响注册主流程。
2. 削峰填谷：高并发下（如秒杀），请求先写入消息队列，消费者慢慢处理。

### 总结：一个复杂业务请求的生命周期

一个“用户下单”请求是如何流转的：

1. 客户端 (View/MVVM)：用户点击下单，前端组装 JSON 数据。
2. 网关 (Gateway)：拦截请求，校验 Token，限流，路由到“订单服务”。
3. API 层 (Controller)：接收请求，DTO 校验，解析参数。
4. 中间件 (Middleware)：记录请求日志，开启分布式追踪 ID。
5. 应用服务 (Application Service)：开启事务。
6. 领域层 (Domain/DDD)：
    1. 加载商品、用户实体。
    2. 调用 `Product.decreaseStock()` (领域行为)。
    3. 调用 `Order.create()` (领域行为)。
7. 基础设施层 (Repository)：将变更写入数据库 (MySQL)。
8. 事件驱动 (Event)：发出“订单创建成功”消息到 MQ。
9. 下游服务：库存服务、通知服务消费消息，执行后续逻辑。
